# Engineering Principles & Culture

We're building product engineers, not code writes based on a given specs. You don't just write code - you own the whole thing from understanding the customer's problem to monitoring it in production. No middlemen. Just engineers solving real problems.

## How We Work

### You Own It

When you build something, you own it. Not just the code - the whole thing:

- The customer problem it solves
- The implementation decisions
- When it breaks at 3am (though hopefully it won't)
- The metrics that show if it's actually working

No pointing fingers. No "that's not my job." You built it, you own it.

### Question Everything

"That's how we've always done it" is not an answer. We expect you to:

- Ask why things are built the way they are
- Propose better ways to do things
- Challenge bad ideas (respectfully)
- Not just follow orders blindly

If something seems dumb, it probably is. Fix it.

### Know the Business

You're not just a coder. You need to understand:

- What problem the customer actually has (not what they say they want)
- How the business makes money
- Why we're building what we're building
- The trade-offs between perfect code and shipping value

Talk to customers. Read support tickets. Look at the data. Then build the right thing.

### Just Do It

Don't wait for someone to tell you what to do:

- See a problem? Fix it
- Have an idea? Try it
- Notice something slow? Speed it up
- Found a bug? Squash it

We hired you to think, not to wait for instructions.

### Automate Everything

If you're doing something thrice, you're doing it wrong:

- Automate deployments
- Automate testing
- Automate monitoring
- Automate the boring stuff so you can do the interesting stuff

Time spent automating is time invested, not wasted.

### Keep It Simple

The best code is the code you don't write:

- Build what's needed today, not what might be needed tomorrow
- Use boring technology that works
- Don't create abstractions until you need them (you probably won't)
- Refactor when things get messy, not before

Clever code is bad code. Write dumb code that works.

### Code Together

We pair program because:

- Two brains are better than one
- Knowledge spreads faster
- Bugs die quicker
- It's more fun

Code review is about making each other better.

### Test Your Stuff

Broken code in production is not a good idea. So:

- Write tests (sometimes first)
- Test the important flows and use cases, not every getter/setter

Quality isn't QA's job. You don't have QA. It's your job.

### AI Is Your Assistant, Not Your Brain

We use AI tools, but:

- You're the engineer, AI is the typist
- Understand what the AI generates (don't just paste and pray)
- Use it for boring stuff: tests, docs, boilerplate
- Your brain does the thinking, AI does the typing

If you can't explain what the code does, you shouldn't ship it.

## How We're Organized

### Everyone Owns Everything

From idea to deployment:

1. Customer has a problem
2. You understand the problem
3. You build a solution
4. You deploy it
5. You monitor if it's working
6. You iterate based on feedback

No handoffs.

### Flat Structure

We don't do hierarchy:

- Senior engineers help, they don't boss
- Everyone's ideas matter
- Best idea wins
- You grow by doing

## Code Quality

Good code is:

- Reviewed before merge (no exceptions)
- Tested (e2e, integration, unit where it makes sense)
- Documented (especially the weird or complicated parts)
- Consistent
- Reusable
- Easy to read and expressive
- Uses domain terminology

---

_If something seems off, propose a change. That's literally the second principle._
